# Контракт артефактов прогона

Версия 1 вводится в сессии V.1. Каталог `runs/<id>/` остаётся источником истины;
контракт нужен браузерному приложению и другим читателям, но не требует базы
данных. Он задаёт границу между рабочим процессом и UI, а не запрещает обмен
данными с работающей моделью.

## Правила совместимости

- Каждый новый JSON-объект содержит `schema_version: 1` и `kind`.
- Читатель принимает только явно поддерживаемые версии и сообщает ошибку вместо
  догадок о неизвестной схеме.
- Старый прогон без `run.json` читается через адаптер из `config.json`,
  `metrics.json` и имени каталога. Адаптер ничего не записывает и помечает
  результат `adapted_from_legacy: true`.
- Старый `metrics.status: ok` нормализуется в `completed`; прежний
  `metrics.json` не меняется, чтобы не ломать раннер, графики и очередь.
- Пути артефактов всегда относительны каталогу прогона и не содержат `..`.

## Граница с работающей моделью

Живым объектом PyTorch владеет только рабочий процесс. Внутри него инспектор
имеет право читать модель после завершения атомарной операции: forward слоя,
полного forward или обновления слоя. Он формирует согласованный сериализуемый
снимок с `run_id`, монотонным `seq`, фазой и шагом. В снимок могут входить
актуальные веса, входы, выходы, активации, learning-сигналы и обновления — в
полном виде для малых моделей либо как ограниченная сводка для больших.

Полученный payload разрешено одновременно сохранить в артефакты и немедленно
передать браузеру по live-каналу. Live-канал не обязан ждать записи и повторного
чтения файла, но использует ту же версионированную схему и номера событий;
файловая копия остаётся канонической для воспроизведения после завершения или
разрыва соединения.

UI может отправлять модели данные и команды через отдельный типизированный
протокол: например, вход для inference, `pause`, `step` или выбор наблюдаемых
тензоров. Рабочий процесс валидирует запрос и применяет его только в безопасной
точке. Запрещены именно передача в UI ссылки на изменяемый Python-объект,
неатомарное чтение тензоров и возможность вызвать произвольный Python-код — не
наблюдение и управление работающей сетью.

Инспекционный payload не является форматом хранения обученной модели. Полное
исполняемое состояние сохраняется отдельно в бинарном `checkpoint.pt`; UI не
должен восстанавливать модель из JSON или загружать checkpoint в свой процесс.

## Интерфейс эксперимента

Каждый модуль `experiments/<name>.py` определяет одну функцию:

```python
def run(config: dict, ctx: RunContext) -> ExperimentResult:
    ...
```

`ExperimentResult.final` — конечные JSON-совместимые метрики. Временные ряды по
шагам/эпохам по-прежнему записываются через `ctx.metrics`. Если эксперимент
обучает PyTorch-модель, он возвращает `ModelArtifacts`: модель, опциональный
optimizer, пример аргументов forward, имена/активации слоёв и номер шага.

Эти живые объекты не покидают worker-процесс. Сразу после возврата раннер
выполняет observation-forward, пишет `model.json` и `checkpoint.pt` и только
затем завершает прогон. Имена файлов, версии схем и атомарная запись принадлежат
раннеру, а не отдельному эксперименту. Ошибка любого из двух экспортов удаляет
оба вновь создаваемых модельных файла и переводит прогон в `failed`, поэтому
успешный моделирующий эксперимент не может оставить половину общего формата.

Эксперимент без модели, например служебный `_selftest`, возвращает только
`final`. Прежний произвольный словарь вместо `ExperimentResult` считается
ошибкой контракта. Backprop-XOR и backprop-MNIST используют один и тот же путь
экспорта; различаются только архитектура и описание слоёв.

Интерактивный XOR реализован отдельным дочерним прогоном
`xor_interactive`. Он получает только `source_run_id`, внутри worker проверяет и
загружает `checkpoint.pt` завершённого `xor_backprop`, а исходный каталог не
изменяет. Перед запуском дочерняя сессия получает копию инспекционного
`model.json` с собственным `run_id`; полный checkpoint остаётся у родителя и не
десериализуется API-процессом.

V.13 заменяет специальную фабрику XOR статическим allowlist-реестром
debug-адаптеров. Сейчас он сопоставляет `xor_backprop → xor_interactive` и
`mnist_mlp_backprop → mnist_interactive`; произвольное имя experiment из
браузера по-прежнему выбрать нельзя. `xor_interactive` остаётся первым
адаптером общего debug-протокола, а не ограничением отладки моделью XOR.
Дочерний конфиг объявляет объект `debug` с полями
`protocol: model_debug_v1`, `renderer`, `accepts_input`, `input_size`,
`supports_step` и `step_scope`, а также adapter-specific `input_mode`, границы и
список `views`. Общие команды, события и snapshots выбираются по capabilities;
renderer определяет только представление данных. Реализованы
`xor_neurons_v1` и `tensor_flow_v1`; второй принимает индекс MNIST
test-примера и не передаёт полные большие тензоры.

## `run.json`

Жизненный цикл worker, разделение main/debug pools и recovery-контракт
описаны в [`worker-lifecycle.md`](worker-lifecycle.md). Итоговый `checkpoint.pt`
остаётся модельным артефактом, а runtime recovery V.10–V.12 хранится отдельно в
`recovery/` и публикуется поколениями.

Манифест жизненного цикла создаётся атомарно до запуска эксперимента и атомарно
заменяется при каждом переходе. Допустимые состояния:
`queued`, `running`, `paused`, `suspended`, `interrupted`, `completed`, `failed`,
`cancelled`. `suspended` означает штатно освобождённый debug worker с проверенным
recovery; `interrupted` — потерянную lease, которую нельзя молча запускать с нуля.

Сессия V.8 реализует переходы кооперативно. `pause` меняет фактический статус
на `paused` только когда worker достиг следующей безопасной точки; `resume`
возвращает `running`. Команда `step` оставляет ручной режим `paused`, но выдаёт
один пропуск через следующую атомарную операцию. `cancel` для queued-задачи
снимает её с executor и сразу завершает манифест, а работающий процесс замечает
отмену в safe point и завершает метрики со статусом `cancelled`, не `failed`.

V.10 добавляет `worker.json` с attempt/pool/heartbeat, отдельный `activity.json`
и `recovery/state.json`. Бинарник recovery неизменяем для одного поколения
(`checkpoint-<generation>.pt`), а `state.json` атомарно переключается последним,
поэтому читатель не смешивает checksum двух поколений. Для XOR event tail
согласуется с recovery после аварии в узком окне между append события и
публикацией следующего state.

V.11 использует тот же механизм для обычного обучения. Versioned adapters
`xor_backprop_v1` и `mnist_mlp_backprop_v1` кладут в checksum-защищённый payload
model/optimizer, метрики, progress cursor, control state и все RNG. MNIST
дополнительно сохраняет permutation эпохи, позицию следующего batch, отдельный
generator и накопители эпохи. `state.json.progress` остаётся малым JSON для UI;
три последних бинарных поколения сохраняются, более старые удаляются только
после атомарного переключения указателя.

Начиная с V.4 веб-очередь сначала атомарно резервирует новый каталог, записывает
клонированный `config.json` и создаёт манифест `queued` с `started_at: null`.
Рабочий процесс меняет его на `running` непосредственно перед настройкой
окружения. `parent_run_id` у повторного запуска указывает на каталог, чей конфиг
был клонирован; цепочка хранит непосредственного родителя, а не только корень.
Исходный каталог при этом не изменяется.

Обязательные для UI поля: `run_id`, `status`, `experiment`, `started_at`,
`updated_at`, `finished_at`, `duration_sec`, `parent_run_id` и словарь
`artifacts`. Время новых прогонов — ISO 8601 с UTC offset.

## `model.json`

Описывает модель без сериализации самой модели: имя, упорядоченный список слоёв,
их типы, входные и выходные формы, активации, число параметров, доступные тензоры
и связи между слоями. `kind` связи отличает forward-канал от learning-канала.
Идентификаторы слоёв уникальны; каждая связь обязана ссылаться на существующие
слои. Поля `captured_at`, `capture_phase` и `step` указывают, в какой безопасной
точке снято включённое в манифест состояние весов. Опциональное
`capture_batch_size` хранит фактический размер ведущего измерения отдельного
observation-forward; это контекст снимка, а не параметр архитектуры слоя.

Сессия V.6 определяет tensor payload версии 1. Каждый тензор содержит:

- `name`, `role`, `shape`, `dtype` и `requires_grad`;
- `value_mode`: `metadata`, `summary` или `full`;
- `summary` с `element_count`, числом конечных и неконечных элементов,
  `min/max/mean/std`, нормами L1/L2 и `sparsity`;
- `values` только в режиме `full`; в режиме `summary` поле
  `values_omitted_reason` объясняет ограничение (`size_limit`, `non_finite`,
  `empty_tensor` или неподдерживаемый JSON dtype).

`std` считается как population standard deviation, а `sparsity` — доля точных
нулей среди всех элементов. При наличии `NaN` или бесконечности статистики
считаются только по конечному подмножеству, их количество остаётся явным, а
полные значения в JSON не встраиваются. Сам контракт запрещает запись
`NaN`/`Infinity`. Для комплексных тензоров числовые статистики относятся к
модулю значения, а raw values пока не включаются.

PyTorch-инспектор не зависит от UI. Он выполняется внутри worker, временно
включает `eval` только для отдельного observation-forward, восстанавливает все
training-флаги и копирует наружу лишь JSON-совместимые данные. В v1 граф строится
по фактическому порядку вызовов leaf-модулей; функциональная активация явно
привязывается к выходу слоя. Для backprop-XOR это линейный граф
`hidden → output`. Его `weight` и `bias` меньше стандартного лимита 256 элементов
и поэтому экспортируются целиком; большие тензоры получают только summary.

Функция инспекции одного тензора формирует тот же payload, что лежит в
`model.json`. В следующих сессиях его можно вкладывать в live-событие или
сохраняемый snapshot без выдачи UI ссылки на исходный storage и без изменения
формата данных.

## XOR forward snapshots

V.9 сохраняет каждый малый согласованный снимок в
`snapshots/<seq>.json` с `kind: xor_forward_snapshot`. Поля `run_id`, `seq` и
`input_command_seq` связывают его с прогоном, событием и конкретной командой
входа. Фаза принимает значения `input`, `forward_hidden` или `forward_output`;
payload содержит два входа, а после вычисления слоя — его `z` и `post`. Снимок
выхода дополнительно сохраняет скрытые активации, вероятность после sigmoid и
бинарное предсказание, чтобы страница после перезагрузки могла целиком
восстановить схему без живой ссылки на модель.

JSON используется здесь намеренно: XOR-снимок содержит единицы чисел и сразу
читается браузером. Для будущих больших тензоров остаётся предусмотрен
`snapshots/<seq>.npz`; событие ссылается на оба формата одинаковым относительным
полем `snapshot`.

Начиная с V.7 карточка запуска читает `model.json` как обычный артефакт и строит
из него граф, панель слоя, tensor summary, числовую таблицу и heatmap. Отсутствие
файла у старого прогона не считается ошибкой. UI проверяет версию, kind,
принадлежность `run_id`, уникальность слоёв и ссылки связей до отрисовки; бинарный
checkpoint в этом пути не открывается.

## XOR train-step snapshots

V.12 добавляет снимок `kind: xor_train_step_snapshot` после целой атомарной
операции backprop-XOR. Он использует тот же `snapshots/<seq>.json` и публикуется
событием `type: xor_train_step`. Снимок содержит `step`, loss, accuracy, признак
фактически выполненного update и оба слоя. Для каждого слоя сохраняются
`weight` и `bias` в трёх состояниях: `before`, точная фактическая `delta` после
Adam и `after`; контракт проверяет одинаковую форму и равенство
`after ≈ before + delta`.

В слой заранее входят nullable-поля `apical_deviation` (`a − baseline`) и
`local_error` (`e`). У backprop они равны `null`, потому что отдельного
апикального канала нет; будущий `ThreeFactorLayer` заполнит их без изменения
renderer или state machine. Снимок также содержит типизированную сетку
`decision_surface`: оси `x0`/`x1` и вероятности после update. UI не загружает
checkpoint и не воспроизводит PyTorch-forward в браузере.

Для обычного запуска интервал автоматически ограничивает историю примерно 200
кадрами и может быть задан `snapshot_every_steps`. После ручного `step` в
paused-режиме кадр сохраняется независимо от интервала. Snapshot сначала
записывается атомарно, затем на него ссылается append-only event, после чего
training recovery публикует `last_event_seq`. Если процесс упал в этом узком
окне, восстановленный детерминированный шаг обязан совпасть с уже сохранённым
payload; существующее событие переиспользуется, а не дублируется.

## Aggregate model-debug snapshots

V.13 добавляет общий `kind: model_debug_snapshot` и событие
`type: model_debug` для renderer больших моделей. Вход описывается типизированно:
для MNIST это `mode: dataset_index`, индекс test-примера, истинная метка, форма
`1×28×28` и preview единственного выбранного изображения. Preview допустим
целиком, потому что это 784 ограниченных значения одного наблюдения, а не поток
весов или датасет.

После каждой атомарной фазы `forward_layer` snapshot содержит все уже
завершённые слои. Запись слоя включает стабильный `layer_id`, полный
`module_path`, тип, activation, число параметров и три `TensorSpec`:
`activation_input`, `preactivation` и `activation_output`. Эти тензоры всегда
имеют `value_mode: summary`: форма, dtype, число finite/non-finite, min/max,
mean/std, L1/L2 и sparsity. Полные активации и параметры в snapshot не
встраиваются. `module_path` позволяет renderer построить иерархию, а порядок
слоёв — поток тензоров без полного графа нейронов.

Последний слой дополнительно публикует prediction и top-3 softmax-класса.
Worker загружает родительский checkpoint и MNIST внутри собственного процесса;
API видит только исходный `model.json`, allowlist adapter и дочерний конфиг.
Snapshot записывается атомарно перед append-only событием, recovery хранит
event cursor и завершённые агрегаты. После crash-window adapter дочитывает
хвост событий и детерминированно пересчитывает нужную промежуточную активацию
из выбранного входа, не сохраняя полный tensor в JSON.

## `checkpoint.pt`

Бинарный checkpoint версии 1 предназначен для inference и продолжения обучения.
Он записывается атомарно через `torch.save` и содержит:

- заголовок `schema_version: 1`, `kind: training_checkpoint`, `run_id`,
  `experiment`, `model_name`, время и `step`;
- полный `model_state_dict`, включая параметры и зарегистрированные buffers;
- `optimizer_state_dict`, если эксперимент использует оптимизатор.

Целый `nn.Module` не сериализуется. При загрузке versioned-код эксперимента
создаёт архитектуру из `config.json`, затем применяет `model_state_dict`.
Checkpoint читается с `torch.load(..., weights_only=True, map_location=...)`,
поэтому загрузка не разрешает произвольное выполнение pickle-кода и может
перенести CUDA-прогон на CPU. Для продолжения обучения после весов загружается
состояние оптимизатора и восстанавливается `step`.

`model.json` и `checkpoint.pt` дополняют друг друга: первый мал, читаем и
пригоден для UI/live-протокола, второй содержит все веса независимо от размера.
Для XOR небольшие параметры дополнительно присутствуют в JSON ради числового
просмотра и heatmap; для больших моделей JSON хранит только summary.

## `events.jsonl`

Одна строка — одно событие с `run_id`, монотонным `seq`, временем `occurred_at`,
`type`, опциональными `step`, `phase`, `layer_id`, скалярами и сообщением.
Большие значения в JSON не встраиваются: поле `snapshot` содержит относительную
ссылку на `snapshots/<seq>.json` для малого XOR payload или агрегированного
model-debug payload; будущий выбранный большой tensor может использовать
`snapshots/<seq>.npz`. Запись завершается переводом строки и `flush`,
поэтому тот же файл можно читать после завершения и показывать через live-tail.

## `commands.jsonl`

Append-only журнал команд версии 1 является межпроцессным mailbox между API и
worker. Каждая полная строка содержит `schema_version`, `kind: run_command`,
`run_id`, строго возрастающий `seq`, `issued_at`, `command` и опциональные
command-specific поля. Допустимые команды: `pause`, `resume`, `step`,
`set_delay`, `set_input`, `cancel`. `delay_ms` разрешён только для `set_delay` и
лежит в диапазоне 0–60000. `input_values` разрешён только для `set_input`; общий
контракт принимает конечный числовой вектор. Сервис сверяет его с capabilities:
V.9 требует ровно два значения для XOR, а V.13 — один целый индекс MNIST в
объявленном диапазоне.

API — единственный писатель журнала внутри приложения; строка дописывается под
lock, завершается `\n`, затем выполняются `flush` и `fsync`. Worker не изменяет
команды и последовательно применяет новые `seq` в `ctx.control.checkpoint()`.
Незавершённый хвост после аварии писателя не исполняется. Благодаря журналу
команды не зависят от памяти HTTP-процесса, а браузер после перезагрузки может
восстановить requested state.

Safe point располагается перед целой атомарной операцией. В текущих
экспериментах это один шаг backprop-XOR, один batch backprop-MNIST или шаг
служебного selftest. В `xor_interactive` новый вход принимается без расходования
step budget, затем скрытый и выходной слой являются двумя отдельными атомарными
операциями. Задержка разбита на короткие интервалы polling: `pause` и `cancel`
могут прервать ожидание до начала следующей операции. Training adapters V.11
публикуют recovery после законченного шага XOR или batch MNIST; V.12 публикует
из той же XOR-фазы train-step snapshot и event, не вводя второй алгоритм
исполнения.
