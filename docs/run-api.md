# API прогонов

Сессия V.2 открыла данные из `runs/<id>/` локальному веб-приложению. Сессия V.4
добавила безопасное клонирование конфига и постановку нового прогона в очередь.
V.5 добавила read-only сравнение запусков.
V.8 добавила типизированные команды активному worker-процессу. Исходные
результаты API не перезаписывает; управление дописывает отдельный журнал команд.
V.9 добавила дочернюю интерактивную XOR-сессию, ручной вход и чтение событий со
ссылками на согласованные snapshots.
V.10 заменила общий scheduler на долговечный `RunSupervisor`: main pool отделён
от disposable debug workers, а suspended/interrupted XOR-сессия продолжает тот
же `run_id` из проверенного recovery-поколения.

Запуск из корня проекта:

```powershell
uv run uvicorn bioplast.viz.api:app --reload
```

По умолчанию читается `./runs`. Другой каталог задаётся переменной окружения
`BIOPLAST_RUNS_DIR` или аргументом `create_app(runs_dir)` в тестах/embedding.
OpenAPI доступен на `/docs`.

Число main и debug процессов задаётся независимо:

```powershell
$env:BIOPLAST_RUN_WORKERS = "2"
$env:BIOPLAST_DEBUG_WORKERS = "2"
uv run uvicorn bioplast.viz.api:app --reload
```

Таймаут отсутствия пользователя по умолчанию — 1800 секунд и настраивается
`BIOPLAST_DEBUG_INACTIVE_TIMEOUT_SEC`. Периоды worker heartbeat/stale и grace
shutdown задаются переменными из [`worker-lifecycle.md`](worker-lifecycle.md).

Браузерный интерфейс доступен на `/runs`: список обновляется автоматически,
карточка прогона показывает параметры, окружение, git provenance, интерактивные
графики Plotly, артефакты и live-tail лога. Plotly.js отдаётся локально самим
приложением, поэтому подключение к интернету не требуется. Пользовательское
описание экранов и элементов управления — в [`run-ui.md`](run-ui.md).

## Маршруты

| Метод и путь | Результат |
|---|---|
| `GET /api/health` | Состояние API и абсолютный каталог runs |
| `GET /api/runs` | Список прогонов и отдельно ошибки повреждённых каталогов |
| `DELETE /api/runs` | Удалить выбранные терминальные запуски одним запросом |
| `GET /api/compare` | Diff конфигов, дельты итогов и общие ряды baseline с кандидатами |
| `GET /api/runs/{id}` | Манифест, конфиг, метрики, артефакты и дочерние debug-сессии |
| `DELETE /api/runs/{id}` | Удалить один терминальный запуск |
| `GET /api/runs/{id}/rerun` | Конфиг и политика редактируемых/зафиксированных полей |
| `POST /api/runs/{id}/rerun` | Создать queued-копию и поставить её в ProcessPoolExecutor |
| `POST /api/runs/{id}/debug` | Создать running-дочернюю сессию XOR-forward из checkpoint |
| `GET /api/runs/{id}/control` | Фактический/requested статус, задержка и доступные команды |
| `POST /api/runs/{id}/control` | Добавить типизированную команду управления активным запуском |
| `POST /api/runs/{id}/activity` | Продлить activity lease видимой debug-сессии после взаимодействия пользователя |
| `GET /api/runs/{id}/events` | Дочитать версионированные события после заданного `seq` |
| `GET /api/runs/{id}/metrics` | Исходный `metrics.json` |
| `GET /api/runs/{id}/log` | Часть UTF-8 лога с байтовыми offset/limit |
| `GET /api/runs/{id}/artifacts` | Рекурсивный список файлов прогона |
| `GET /api/runs/{id}/artifacts/{path}` | Содержимое одного артефакта |

После V.7 карточка запуска находит `model.json` в списке артефактов и читает его
через обычный маршрут артефакта. Backprop-XOR и backprop-MNIST создают его через
единый `ExperimentResult` и централизованный экспорт раннера. Отдельный model
endpoint не нужен: UI получает тот же канонический файл, а live-доставка в
следующих сессиях будет использовать идентичный tensor payload. Полный
`checkpoint.pt` доступен тем же маршрутом как бинарное скачивание, но backend и
браузер UI его не десериализуют: запуск и дообучение остаются ответственностью
worker-процесса.

Список фильтруется параметрами `status` (можно повторять), `experiment`, `seed`,
`started_after`, `started_before`; `include_debug=false` исключает debug-сессии,
а `offset` и `limit` задают пагинацию. Каждый элемент содержит `is_debug`,
вычисленный по capability, а ответ — `counts` по всему отфильтрованному набору.
Новые и legacy-прогоны возвращаются в одной нормализованной форме.

`DELETE /api/runs` принимает `{"run_ids": ["run-a", "run-b"]}`. Удаление
необратимо, поэтому разрешено только для `completed`, `failed` и `cancelled`.
Запрос сначала валидирует весь набор: если в нём есть активный запуск или у
выбранного родителя остаётся невыбранный ребёнок, сервер отвечает `409` и ничего
не удаляет. Неизвестный или небезопасный идентификатор отвечает `404`, пустой
список — `422`. Одиночный маршрут применяет ту же политику.

Лог читается порциями с целевым размером до 1 МиБ; сервер может дочитать до трёх
байт, чтобы не разрезать UTF-8-символ. Ответ содержит `next_offset` и `eof`,
поэтому UI делает live-tail без повторной передачи всего файла.

## Сравнение запусков

`GET /api/compare` принимает один `baseline` и от одного до четырёх повторяемых
параметров `candidate`:

```text
/api/compare?baseline=run-a&candidate=run-b&candidate=run-c
```

Идентификаторы должны быть различными. Ответ содержит:

- нормализованные сведения о baseline и кандидатах;
- `config_diff` только для отличающихся полей верхнего уровня `config.json`;
  служебный `parent_run_id` в diff не входит;
- числовые `final_metrics` с абсолютной дельтой `candidate - baseline` и
  относительной дельтой только при ненулевом baseline;
- `metric_series` с исходными координатами каждого запуска по `step` или
  `epoch`, без интерполяции отсутствующих точек;
- `warnings` для различий эксперимента, датасета, модели и оси шага.

У каждого ряда отдельно перечислены `missing_run_ids`: отсутствие метрики не
подменяется нулями и не скрывается. Невалидный набор идентификаторов возвращает
422, отсутствующий запуск — 404.

## Повторный запуск

`POST /api/runs/{id}/rerun` принимает полный клон исходного конфига:

```json
{
  "config": {
    "experiment": "xor_backprop",
    "dataset": "xor",
    "model": "mlp-2-8-1",
    "seed": 7,
    "hidden": 8,
    "steps": 2000,
    "lr": 0.01
  }
}
```

Сервер повторно читает оригинал и проверяет, что набор ключей не изменён.
Редактировать можно существующие JSON-скаляры и списки скаляров. Зафиксированы
`experiment`, `session`, `dataset`, `model`, `tag`, `id`, `parent_run_id`, поля
путей (`*_path`, `*_root`, `*_dir`, `*_file`) и сложные вложенные структуры.
Тип каждого редактируемого значения сохраняется; `device` дополнительно
ограничен значениями `auto`, `cpu`, `cuda` и `cuda:N`. Так UI не может выбрать
произвольный Python-модуль или путь на машине.

Успешный ответ имеет статус `202 Accepted` и содержит новый `run_id`, статус
`queued`, `parent_run_id`, список фактических изменений и URL карточки. Каталог
нового прогона резервируется атомарно до ответа: в нём уже лежат клонированный
`config.json` и `run.json`. Процесс очереди переводит манифест в `running`, затем
в `completed` или `failed`. Повторный запуск доступен только после перехода
исходного прогона в терминальное состояние.

## Управление запуском

`GET /api/runs/{id}/control` возвращает:

- `status` — фактическое состояние из `run.json`;
- `requested_status` — состояние, заданное уже записанными командами, которое
  worker может ещё не успеть применить;
- текущую `delay_ms`, последний `last_command_seq` и `available_commands`;
- `lifecycle`: pool, текущую worker/activity lease, recovery generation,
  возможность resume и явную причину недоступности.

`POST /api/runs/{id}/control` принимает одну команду:

```json
{"command": "pause"}
```

Для задержки требуется значение от 0 до 60000 мс:

```json
{"command": "set_delay", "delay_ms": 250}
```

В режиме `running` доступны `pause`, `set_delay`, `cancel`; в запрошенном или
фактическом `paused` — `resume`, `step`, `set_delay`, `cancel`. Queued-запуск
можно заранее поставить на паузу или замедлить. Повторные несовместимые команды
возвращают 409, неверный payload — 422, успешная запись в `commands.jsonl` —
`202 Accepted` с записанной командой и обновлённым control state.

В `suspended`/`interrupted` команды `resume`, `step` и `set_input` доступны
только при валидном checksum и совместимом recovery adapter. Команда сначала
продлевает activity lease, затем будит новый debug-процесс; обычные команды
живому worker процесс не пересоздают. `cancel` завершает неактивную сессию без
создания worker. Фоновый GET/polling lease не продлевает.

Control state также возвращает объект `debug` из capabilities сессии и
`accepts_input`. UI не определяет отладочный режим по имени эксперимента:
`supports_step` включает пошаговое управление, `accepts_input` и `input_size` —
типизированный ввод, а `renderer` выбирает модельно-зависимое представление
snapshots.

`step` означает одну следующую safe-point операцию, а не произвольную строку
Python. Для обучения это шаг XOR или batch MNIST. В `xor_interactive` команда
`set_input` с двумя конечными `input_values` выбирает вход, не расходуя step;
следующие два шага вычисляют скрытый и выходной слой. `resume` выполняет обе
фазы без остановки, но после полного forward worker снова ждёт новый вход.
Отмена queued-задачи пытается снять Future с scheduler и сразу пишет
терминальный контракт. Running-задача завершается кооперативно в worker, поэтому
API не убивает дерево процессов посреди обновления весов.

В V.9 `POST /api/runs/{id}/debug` имеет реализованный адаптер только для
завершённого `xor_backprop` с
`model.json` и `checkpoint.pt`. Сервер резервирует новый каталог, записывает
`parent_run_id`, копирует малый инспекционный manifest с новым `run_id`, заранее
передаёт сессию debug-очереди supervisor в непрерывном режиме. Для послойного forward
пользователь сначала отправляет `pause`. Сам checkpoint читает
только дочерний worker. Ответ `202 Accepted` содержит URL новой карточки.
Ограничение относится к набору реализованных адаптеров, а не к общему
debug-протоколу: другие модели подключаются собственным loader/input adapter и
renderer без изменения машины управления.

`GET /api/runs/{id}/events?after_seq=N` возвращает только события с большим
монотонным номером и `last_seq`. Событие `xor_forward` ссылается на JSON snapshot
через обычный защищённый маршрут артефактов; отсутствие новых событий — пустой
список, а не ошибка.

## Граница безопасности

`run_id` обязан быть именем непосредственного подкаталога `runs/`. Артефакт
после разрешения `..`, абсолютных путей и симлинков обязан остаться внутри
каталога выбранного прогона. Нарушение границы возвращает 404 и не раскрывает
файл. Повреждённый контракт конкретного прогона возвращает 422; при запросе
списка он не роняет весь каталог, а появляется в массиве `errors`.
