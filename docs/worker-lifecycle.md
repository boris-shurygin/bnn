# Воркеры, пулы и восстановление запусков

Этот документ описывает текущую схему V.9 и целевой контракт V.10. Цель V.10 —
не только освободить основной пул от долгоживущих debug-сессий, но и позволить
продолжить тот же запуск после гибернации worker, падения процесса, перезапуска
сервера или отключения питания.

## Гарантии

После V.10 должны выполняться следующие инварианты:

- каталог `runs/<run_id>/` является единственным долговечным источником истины;
- UI и API никогда не владеют живой моделью PyTorch;
- одновременно один запуск исполняет не более одного worker;
- завершённые модельные артефакты не смешиваются с recovery-состоянием;
- пауза и восстановление происходят только на safe point;
- активная debug-сессия сохраняет один worker при паузах, шагах и переключении
  режимов; только длительное отсутствие пользователя освобождает процесс;
- `resume`, `step` или новый вход будят suspended debug-сессию в новом процессе;
- после аварии продолжается тот же `run_id`, история команд, событий и логов;
- если восстановление невозможно, запуск остаётся доступен для инспекции и явно
  сообщает причину, а не исчезает и не начинает вычисление сначала молча.

Recovery гарантирует продолжение с последней записанной safe point. Работа после
неё может быть потеряна, но уже зафиксированная атомарная операция не повторяется
и не применяется наполовину.

## Кто чем владеет

### Uvicorn / FastAPI

API принимает команды, валидирует их, читает файловые контракты и передаёт
намерение `RunSupervisor`. API не загружает `checkpoint.pt` и не хранит ссылки на
модель, optimizer или тензоры worker.

### `RunSupervisor`

Один supervisor внутри серверного процесса владеет очередями, worker leases,
heartbeat и reconciliation при старте. Его память — кэш текущего состояния, но
не источник истины: после перезапуска registry восстанавливается из `runs/`.

Supervisor отвечает за:

1. атомарный claim запуска перед созданием процесса;
2. выбор main или debug executor;
3. недопущение двух worker для одного `run_id`;
4. перевод stale lease в recoverable-состояние;
5. запуск resume-attempt из recovery-checkpoint;
6. ограниченное ожидание worker при shutdown сервера;
7. явную диагностику аварийного завершения процесса.

### Main pool

Обычные обучающие и оценочные запуски выполняются ограниченным
`ProcessPoolExecutor`. Размер задаётся `BIOPLAST_RUN_WORKERS`. Очередь этого пула
не должна содержать debug-сессии.

### Debug supervisor

Каждая активная debug-сессия получает один `spawn`-процесс вне main pool и
сохраняет его на всё время пользовательской активности. `pause`, `resume`,
`step` и подача нескольких входов обслуживаются тем же процессом без повторной
загрузки модели. Число одновременно активных debug-процессов ограничивается
`BIOPLAST_DEBUG_WORKERS`; остальные сессии остаются queued/suspended.

Штатно debug-процесс завершается только после session-inactivity timeout в
безопасном состоянии, явного завершения сессии или остановки сервера. Таймаут —
это гибернация с предварительной записью recovery-checkpoint, а не `terminate()`
посреди матричной операции. Новый процесс создаётся при следующей активности
только если прежний уже `suspended`/`interrupted` или исчез при перезагрузке
машины.

Activity lease имеет скользящий срок действия и продлевается на месте. Команда,
клик или heartbeat не создают новую lease и не перезапускают worker. Свежий
процесс создаётся один раз при создании сессии либо при пробуждении
`suspended`/`interrupted`. Стандартный
`ProcessPoolExecutor` освобождает future, но сохраняет сам процесс и может не
вернуть память большой модели операционной системе.

### Activity lease debug-сессии

Вычислительный режим и пользовательская активность — разные понятия. `paused`
не означает inactive: пользователь может долго изучать веса, делать отдельные
шаги и переключаться между представлениями, сохраняя загруженную модель.

Activity lease продлевают:

- `pause`, `resume`, `step`, `set_delay`, `set_input` и другие явные команды;
- открытие карточки debug-сессии;
- throttled heartbeat видимой вкладки, только если после прошлого heartbeat в
  ней были pointer/keyboard interactions.

Фоновый polling состояния, событий и логов сам по себе lease не продлевает:
забытая открытая вкладка не должна держать GPU/CPU-память бесконечно. Heartbeat
интерфейса не является worker heartbeat: первый доказывает присутствие
пользователя, второй — жизнь процесса.

Recovery обновляется на safe points всё время, пока worker жив, а не только перед
таймаутом. Поэтому внезапная смерть процесса и штатная гибернация используют один
и тот же последний согласованный checkpoint.

## Состояния запуска

Целевой автомат расширяет существующие состояния:

| Статус | Worker | Значение |
|---|---:|---|
| `queued` | нет | запуск ожидает свободный слот |
| `running` | есть | worker выполняет атомарные операции |
| `paused` | есть | worker остановлен на safe point; activity lease ещё действует |
| `suspended` | нет | состояние сохранено, worker освобождён штатно |
| `interrupted` | нет | lease оборвалась неожиданно; допустим resume из проверенного recovery |
| `completed` | нет | успешное терминальное состояние |
| `failed` | нет | невосстановимая ошибка эксперимента или recovery |
| `cancelled` | нет | пользователь окончательно завершил запуск |

`suspended` и `interrupted` не терминальны. `cancelled` терминален и не означает
паузу. UI должен называть команду явно: «Завершить сессию», а не использовать её
как способ выйти из пошагового режима.

Основные переходы:

```text
queued ──claim──> running <──resume/pause──> paused
                    │                          │
                    └──────────┬───────────────┘
                               │ session inactivity at safe point
                               ▼
                         checkpoint ──> suspended
                                            │
                               activity/wake│
                                            ▼
                                         running

running/paused ──process/server/power loss──> interrupted ──resume──> running
running ──success──> completed
running ──experiment error──> failed
any nonterminal ──cancel──> cancelled
```

`paused` и `waiting_input` сами по себе не запускают отдельный таймер уничтожения
процесса. Supervisor смотрит только на скользящую activity lease всей сессии.
Пока пользователь работает с видимой вкладкой или отправляет команды, lease
продлевается, а один и тот же worker остаётся жив. После длительного отсутствия
пользователя `paused` и `waiting_input` становятся удобными safe points для
гибернации. `set_input` будит suspended-сессию так же, как `resume`.

## Долговечные файлы

### Неизменяемые и итоговые артефакты

- `config.json` — исходная конфигурация и debug capabilities;
- `commands.jsonl` — append-only команды пользователя;
- `events.jsonl` — append-only наблюдения worker;
- `snapshots/` — версионированные UI-снимки;
- `checkpoint.pt` — итоговая/публикуемая модель, создаётся при успешном
  завершении или явном экспорте и не служит runtime-lease.

### Recovery-артефакты

```text
runs/<run_id>/recovery/
  state.json       # версия, attempt, safe-point cursor, command/event seq,
                   # progress, checkpoint checksum, время записи
  checkpoint.pt    # model, optimizer и adapter-specific state
  rng.pt           # Python/NumPy/torch CPU/CUDA RNG при необходимости
```

Запись выполняется во временный файл в том же каталоге, затем заменяется
атомарно. `state.json` публикуется последним и содержит checksum бинарных файлов.
Checkpoint считается пригодным только после полной валидации всего набора.

Recovery payload обычного обучения содержит как минимум:

- `model.state_dict()` и `optimizer.state_dict()`;
- epoch, batch, global step и фазу внутри эксперимента;
- состояние sampler/permutation, чтобы не повторять и не пропускать данные;
- Python, NumPy, torch CPU и torch CUDA RNG;
- накопленные метрики и последний опубликованный event seq;
- последний применённый command seq и requested control mode;
- версию resume-adapter эксперимента.

Debug payload дополнительно содержит текущий вход, последнюю завершённую фазу,
нужные для следующей фазы активации и ссылку на последний согласованный snapshot.
Для XOR recovery пишется после `input`, `forward_hidden` и `forward_output`,
поэтому новый worker продолжает именно со следующего слоя.

### Runtime lease и heartbeat

`worker.json` описывает только текущего владельца исполнения:

- supervisor instance id;
- process id и уникальный attempt;
- pool kind (`main` или `debug`);
- `claimed_at`, `heartbeat_at`, requested/actual worker state;
- recovery generation, из которой стартовал worker.

Lease не содержит единственную копию научного состояния. После power loss stale
lease можно отбросить, если recovery-набор валиден.

## Схемы запуска

### Новый обычный запуск

1. API атомарно создаёт каталог и `run.json: queued`.
2. Supervisor ставит `run_id` в main queue.
3. Свободный worker получает lease и переводит запуск в `running`.
4. Эксперимент периодически пишет recovery на safe point.
5. При успехе runner создаёт итоговые артефакты и `completed`.

### Новая debug-сессия

1. Adapter проверяет родительский checkpoint и создаёт дочерний `run_id`.
2. Сессия попадает только в debug queue.
3. Debug worker загружает модель внутри собственного процесса.
4. После каждой фазы публикуются snapshot/event и recovery generation.
5. Пока activity lease продлевается, тот же процесс обслуживает все входы и
   шаги. После session-inactivity timeout worker пишет recovery, переводит
   сессию в `suspended` и завершается.

### Возобновление debug-сессии

1. API дописывает `resume`, `step` или `set_input` в `commands.jsonl`. Если
   worker ещё жив, он применяет команду без перезапуска процесса.
2. Supervisor атомарно claim-ит suspended/interrupted сессию.
3. Новый debug worker проверяет checksum и версии recovery.
4. Adapter восстанавливает модель, вход, фазу и command/event cursors.
5. Выполнение продолжается со следующей атомарной операции; старые события не
   дублируются.

### Перезапуск сервера или отключение питания

При старте supervisor выполняет reconciliation:

1. сканирует все нетерминальные `run.json`;
2. проверяет lease heartbeat и наличие живого локального процесса;
3. `queued` возвращает в соответствующую очередь;
4. stale `running`/`paused` переводит в `interrupted`;
5. валидирует recovery generation и показывает возможность resume;
6. suspended debug не запускает до команды пользователя;
7. обычный interrupted run возобновляет автоматически только при явно выбранной
   политике; безопасное значение по умолчанию — подтверждение из UI.

Graceful shutdown сначала запрещает новые claim, затем просит workers записать
recovery и освободить lease. После ограниченного таймаута оставшиеся процессы
завершаются supervisor, а запуск остаётся `interrupted`, не `failed`.

### Отмена

`cancel` остаётся терминальной операцией. Running worker замечает её на safe
point; queued/suspended/interrupted запуск завершается API без создания worker.
Recovery можно оставить для аудита, но команда resume после `cancelled`
недоступна.

## Resume-adapter эксперимента

Общий runner не может угадать локальные переменные произвольного Python-кода.
Эксперимент, поддерживающий recovery, объявляет версионированный adapter:

- `capture_recovery(ctx) -> payload`;
- `restore_recovery(payload, ctx) -> experiment state`;
- атомарные safe points и progress cursor;
- совместимость версии кода/config/checkpoint;
- максимальную допустимую потерю работы между checkpoint.

Если adapter отсутствует, запуск после аварии остаётся `interrupted` и доступен
для просмотра, но UI честно отключает resume. Нельзя молча запускать experiment
сначала под тем же `run_id`.

Для MNIST первым практическим recovery-контрактом будет checkpoint после batch
или через настраиваемое число batch. Для точного продолжения сохраняются
optimizer, permutation текущей эпохи и позиция batch. Для XOR стоимость мала,
поэтому recovery можно писать после каждого шага.

## Настройки

Целевые переменные окружения:

| Переменная | Назначение | Безопасное значение по умолчанию |
|---|---|---:|
| `BIOPLAST_RUN_WORKERS` | процессы main pool | `1` |
| `BIOPLAST_DEBUG_WORKERS` | одновременно активные debug-процессы | `2` |
| `BIOPLAST_DEBUG_INACTIVE_TIMEOUT_SEC` | отсутствие активности пользователя до гибернации | `1800` |
| `BIOPLAST_RECOVERY_EVERY_STEPS` | частота recovery обычного обучения | adapter-specific |
| `BIOPLAST_WORKER_HEARTBEAT_SEC` | период heartbeat | `5` |
| `BIOPLAST_WORKER_STALE_SEC` | порог stale lease | `30` |
| `BIOPLAST_SHUTDOWN_GRACE_SEC` | ожидание recovery при shutdown | `15` |

## Что видит пользователь

Карточка запуска должна показывать:

- pool и текущий worker/attempt;
- время последней пользовательской активности и остаток activity lease;
- время последнего heartbeat и recovery checkpoint;
- `paused`, `suspended` и `interrupted` как разные состояния;
- кнопку «Продолжить» для recoverable-состояния;
- причину, если resume недоступен;
- оценку возможной потери работы после последнего checkpoint;
- отдельную терминальную кнопку «Завершить запуск/сессию».

Закрытие вкладки браузера не отменяет и не завершает запуск.

## Текущее ограничение V.9

Сейчас веб-приложение создаёт один общий `RunScheduler`; его размер по умолчанию
равен одному. Долгоживущая debug-сессия поэтому блокирует обычный MNIST в очереди,
а `shutdown(wait=False)` не является протоколом восстановления. Текущие
`checkpoint.pt` и snapshots достаточны для инспекции, но ещё не являются полным
recovery-контрактом. До реализации V.10 перезапуск активного worker нельзя считать
безопасным и воспроизводимым resume.
