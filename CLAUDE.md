# bnn — биологически правдоподобное локальное обучение

Хобби-исследовательский проект: локальные three-factor правила обучения с сегрегированным апикальным каналом, как альтернатива backprop. Проверка на XOR, MNIST, возможно CIFAR-10.

## Документы

- `docs/research-plan.md` — что и почему: гипотезы, архитектура схемы, методология, литература
- `docs/roadmap.md` — план работ по сессиям, оценки, требования к железу, гигиена процесса
- `LOG.md` — журнал сессий; **каждая сессия заканчивается записью с полем «следующее действие»**

Перед содержательной работой сверяйся с `research-plan.md`: терминология и формулы там.

## Ключевые термины

- **forward-канал (базаль)** — обычное вычисление `post = activation(W_ff · pre)`
- **апикальный канал (learning)** — отдельный вход `a`, влияет **только** на пластичность, на forward-выход не влияет никогда
- **`e = a · psi(z)`** — локальная ошибка нейрона; `psi` — псевдопроизводная (`1[z>0]` для ReLU), заменяет `f'`
- **`W_fb`** — матрица доставки learning-сигнала, случайная фиксированная с нулевым средним. **Не** транспонированная `W_ff` (кроме режима верификации)
- **trace** — eligibility trace, затухающая память о ко-активации
- **`K`** — размерность learning-сигнала: 1 (скалярный дофамин) … dim(выход) (полная DFA)

## Конвенции реализации — не нарушать

Это сознательные отклонения от обычного PyTorch, не недосмотр.

- **Не использовать AMP / fp16 для локальных правил.** `lr · outer(e, pre)` — крошечное слагаемое к весу порядка единицы, в fp16 округляется до нуля молча. Loss scaling отсутствует, поскольку нет оптимизатора. Веса и обновления только fp32. TF32 включать можно и нужно.
- **Не заменять ручное обновление весов на `torch.optim`.** Обновления локальные и ручные по определению; autograd используется исключительно как калькулятор эталонного градиента для диагностики alignment.
- **Апикальный сигнал не добавляется к forward-выходу.** Сегрегация каналов — проверяемая гипотеза проекта, а не деталь реализации.
- **Learning-сигнал всегда используется как отклонение от baseline** (`a − baseline`). Без вычитания — runaway.
- **`softmax` в WTA-слоях — по каналам (`dim=1`), не по пространству.** Ошибка тихая: сеть просто учится плохо.
- **Датасет целиком в VRAM, `DataLoader` не использовать.** MNIST 188 МБ, CIFAR-10 614 МБ. На Windows `num_workers>0` особенно медленный из-за `spawn`.
- **`pathlib.Path` везде**, никакой конкатенации путей строками.
- **Очередь прогонов — на Python** (`ProcessPoolExecutor`), не shell-скрипт: должно работать одинаково на Windows, в WSL и в облаке.
- **Наблюдаемая очередь резервирует каталог до `submit`.** Сначала атомарно создаются `runs/<id>/`, клонированный `config.json` и манифест `queued`, только затем задача передаётся в `ProcessPoolExecutor`. Иначе UI не знает новый `run_id`, не видит ожидание и не может отличить очередь от потерянной задачи.
- **Повторный запуск из браузера не выбирает код и пути.** `experiment`, модель, датасет и поля путей сохраняются от исходного прогона; менять можно только существующие JSON-скаляры и списки скаляров с сохранением типа. Новый прогон получает `parent_run_id`, исходный каталог никогда не изменяется.
- **Все эксперименты возвращают `ExperimentResult`.** Финальные метрики лежат в
  `final`; PyTorch-модель, optimizer и пример входа передаются worker-раннеру
  через `ModelArtifacts`. Эксперимент не пишет канонические `model.json` и
  `checkpoint.pt` самостоятельно: раннер создаёт оба файла общей политикой и
  не оставляет частичный набор при ошибке экспорта.
- **Длительный эксперимент отмечает безопасные точки через `ctx.control`.**
  `checkpoint()` вызывается только перед атомарной операцией обучения: сейчас
  это шаг XOR или batch MNIST. Команды `pause`, `step`, `resume`, `set_delay` и
  `cancel` читаются worker-процессом из типизированного `commands.jsonl`; нельзя
  проверять произвольный UI-флаг посреди обновления весов или заводить отдельный
  алгоритм для пошагового режима.
- **UI не владеет живой моделью, но live-обмен с ней разрешён и необходим.**
  Объект PyTorch остаётся внутри рабочего процесса. Инспектор может читать его
  состояние в согласованных точках между атомарными операциями, сериализовать
  веса, активации и другие диагностические данные и сразу передавать их UI через
  версионированные события/снимки. Команды из UI идут обратно через явный
  типизированный протокол и применяются в безопасных точках; прямые ссылки на
  изменяемые тензоры и произвольные вызовы Python через UI запрещены.
- **Раннер печатает `torch.cuda.is_available()` и имя устройства** в лог каждого прогона. На Windows легко случайно поставить CPU-сборку torch.
- **Каждый прогон пишет в свою папку** `runs/<id>/`. Windows блокирует открытые файлы, параллельная запись в общий лог упадёт.
- **Ускорение искать в параллельных процессах, а не в GPU-коде.** Замерено на блоке 0: MNIST `784→256→10` даёт всего 1.3× на 3060 против CPU — узкое место не вычисления, а задержки запуска ядер. До блока 4 карта простаивает, поэтому `--workers 3..4` даёт больше, чем любая оптимизация под GPU.

## Структура

```
src/bioplast/
  layers/       ThreeFactorLayer, HebbLayer, ConvHebbLayer, LocallyConnected
  signals/      источники апикального сигнала (supervised / predictive / reward)
  delivery/     W_fb: random, topographic, learnable, transposed
  diagnostics/  alignment, runaway, win-histogram, sparsity
  runner/       config → run → metrics.json
  viz/          plot.py, report.py
experiments/    скрипты конкретных экспериментов
runs/           результаты прогонов (в .gitignore)
docs/
```

**Источник апикального сигнала — подключаемый объект, а не `if` внутри слоя.** Вся гипотеза 1 держится на переключаемости режимов UL/SSL/supervised/RL сменой источника.

**Правило трёх:** код выносится в `src/` только когда одно и то же написано трижды. В блоках 0–2 дублирование в `experiments/` допустимо.

## Тесты

Центральный тест корректности: при `W_fb = W_ffᵀ` величина `e` должна совпадать с `δ` из autograd. Это отделяет баги реализации от вопросов «работает ли идея».

**Сначала подозревай измеритель, потом гипотезу.** В блоке 0 три дефекта из четырёх оказались в отчётности, а не в вычислениях: критерий «XOR решён» срабатывал на случайной инициализации, имя карты печаталось для CPU-прогонов, стрелка в логе выдавала совпадение за следствие. Проект, у которого главный продукт — измерения, а ожидаемый результат — отрицательный, не отличает сломанный измеритель от сломанной идеи иначе как проверкой.

**На «а точно ли работает X» отвечать замером и автопроверкой, а не заверением.** Пример из блока 0: пиковая VRAM, равная нулю при `device=cuda`, означает, что эксперимент проигнорировал `ctx.device`; теперь это warning в логе и два теста. Замер, который нельзя повторить одной командой, не считается.

**Изменения `ProcessPoolExecutor` проверять настоящим Windows `spawn`.** Подмена scheduler в тесте проверяет API-контракт, но не импорт дочернего процесса, переходы `queued → running → terminal` и кодировку его stdout. Нужен хотя бы один короткий end-to-end прогон через реальный process pool.

## Логи и имена артефактов

Читатель лога — это вы через неделю, без памяти о том, как писался код. Формально верной строки мало.

- **Полная дата, а не только время.** «14:30:12» без числа бесполезно при разрывах между сессиями.
- **Рядом с «что» писать «почему».** `устройство прогона: CPU — задано в конфиге (device=cpu)`, а не просто `device=cpu`.
- **Независимые факты — отдельными строками.** `is_available() = True → вычисления на CPU` читается как следствие, хотя это совпадение: XOR намеренно идёт на CPU при исправной карте.
- **Консольный лог дочернего процесса учитывает `sys.stdout.encoding`.** На Windows worker может получить CP1251 даже при UTF-8-файле лога; неподдерживаемый символ не должен вызывать traceback внутри `logging`. Файловый лог остаётся UTF-8, консольный formatter безопасно транслитерирует или заменяет символ.
- **Имя папки прогона временно́е и самоописательное:** `20260808-100014-ses0.4-mnist-mlp-784-256-10-s0-bp`. Метка времени первой компонентой — сортировка по имени совпадает с хронологической.
- **Имя файла конфига в очереди — детерминированное, без времени.** Перегенерация свипа должна перезаписывать те же файлы, а не плодить дубли. Отсюда две функции: `make_run_id` и `config_slug`.

Проверка любой строки двумя вопросами: поймёт ли её человек через неделю; не прочитается ли она иначе рядом с соседним прогоном.

## Процесс

- **Все изменения через ветку.** Единственное исключение — `LOG.md`: журнал правится **только на `main`**, в том числе для фиксации промежуточного вывода из ещё не влитой ветки. Иначе вывод исчезнет вместе с веткой, а это ровно то, что ценнее кода.
- Монополия `main` на `LOG.md` попутно означает, что конфликтов при мерже не бывает. Перед мержем — `git rebase main`, чтобы история осталась линейной.
- **Гипотеза не подтвердилась:** сначала `git tag exp/<имя>` (тег переживает удаление ветки, коммиты иначе уедут в сборку мусора), потом `git branch -D`. Вывод к этому моменту уже на `main`.

### Совместная работа Claude Code и Codex

- `CLAUDE.md` — единый источник проектных правил для обоих агентов. `AGENTS.md` служит адаптером для Codex и не дублирует содержимое этого файла.
- **Одна задача — один ответственный агент и одна ветка.** Начавший задачу агент доводит исправления после ревью до завершения.
- Последовательная работа допустима в одном чистом рабочем каталоге. Для параллельной работы обязательны отдельные `git worktree`: два агента не редактируют один рабочий каталог одновременно.
- Второй агент сначала проводит независимое ревью зафиксированного diff: проверяет код, тесты, измерения и научные допущения, не переписывая реализацию без отдельного поручения.
- Передача задачи между агентами содержит ветку или коммит, изменённые файлы, выполненные проверки, открытые вопросы и следующий шаг.
- `LOG.md` обновляет только интегратор, работающий на `main`; агенты в рабочих ветках передают ему выводы, но не редактируют журнал.

## Стиль

- Ноутбуки — только для разведки. Библиотечный код в ноутбуках не живёт никогда.
- Правки в документах — по разделам, отдельными дифами, не пачкой.
- Отрицательные результаты фиксируются наравне с положительными: «где именно ломается alignment» ценнее очередного процента точности.
- Расшифровывать ML-сокращения при первом употреблении (`AMP` — Automatic Mixed Precision), не снижая глубины по существу.
