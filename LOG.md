## 0.1–0.6 — блок 0: каркас и точка отсчёта (2026-08-08)

Шесть сессий роадмапа сделаны подряд, одной серией. Ниже — по пунктам плана.

**Сделано.**

*0.1 Репозиторий и окружение.* `uv` 0.12.3 (`~/.local/bin`), venv на CPython
3.12.10, torch 2.6.0+cu124 из индекса PyTorch, `torch.cuda.is_available() = True`,
RTX 3060 видна. `pyproject.toml` + `uv.lock`, `.gitattributes` с `eol=lf`,
`runs/`, `queue/`, `data/` в `.gitignore`. Каркас `src/bioplast/`, `experiments/`,
`tests/`. pytest — 22 теста, зелёные.

*0.2 Журнал и раннер.* Этот файл. Раннер: конфиг-файл → `runs/<id>/{config,metrics}.json`
+ `run.log`; идентификатор короткий (`mnist-bp-s0-d0a098`) из-за лимита пути в
260 символов. Очередь — `ProcessPoolExecutor` с параметром `--workers`.
Падение эксперимента пишется в `metrics.json` со `status: failed` и очередь не
роняет. `bioplast.runner.sweep` разворачивает базовый конфиг по сетке значений
(`--set seed=0,1,2`) — свипы блока 2 не придётся писать руками.

*0.3 XOR-эталон.* `2→8→1`, ReLU, BCEWithLogits, Adam lr=0.05. Три сида, все
решают: loss `1e-5…7e-5`, точность 1.00, решение на шагах 43 / 43 / 49 из 2000.

*0.4 MNIST-эталон.* `784→256→10`, Adam lr=1e-3, батч 128, 10 эпох. Тест
**98.06 / 98.08 / 97.90 %** на сидах 0/1/2 — ориентир роадмапа (~98%) взят.
Датасет качается скриптом с зеркала OSSCI, кэшируется в `.npz` и целиком уезжает
на GPU; `DataLoader` не используется.

*0.5 Диагностика v0.* `diagnostics/`: регистратор метрик с плоскими ключами
`группа/имя` и замеры — нормы весов, нормы градиентов, RMS / максимум / разреженность
активаций. `act_max` заведён сразу как сторож runaway для абляции §3.5.

*0.6 `plot.py`.* `metrics.json` → PNG по одной группе метрик на файл. Скрипт не
знает ничего про конкретный эксперимент: новая метрика в эксперименте
автоматически появляется на графике.

**Сломалось.**

- Store-сборка Python (`WindowsApps`) — неудобная база для venv; `uv` создал
  окружение поверх неё без проблем, но при первой же странности стоит перевести
  проект на `uv python install`.
- Первая версия критерия «XOR решён» смотрела только на точность. На четырёх
  точках случайная инициализация угадывает все четыре с вероятностью 1/16, и
  прогон рапортовал «решено на шаге 6». Критерий ужесточён до «точность 1.0 **и**
  loss < `loss_target`» — стало 43–49.
- `np.frombuffer` отдаёт read-only массив, torch на это ругается; добавлен `.copy()`.
- `python -m bioplast.viz.plot` предупреждал о двойном импорте (модуль
  реэкспортируется в `__init__`); CLI вынесен в `viz/__main__.py`.

**Замеры для памяти.** XOR (CPU) — 7.5 с на прогон, из них секунды на импорт
torch. MNIST (GPU) — 12 с последовательно, 9.2 с при трёх параллельных процессах:
карта не загружена, параллельность работает ровно так, как обещал роадмап.
Свип из 45 конфигураций блока 2 — это порядка 7 минут, а не полутора часов.

## 0.9 — привязка прогона к состоянию кода (2026-08-08)

**Сделано.** `metrics.json` теперь содержит блок `git`: хеш коммита, ветка,
признак незакоммиченных правок и список изменённых файлов.

Дыра была настоящая: `runs/` не версионируется, и через месяц по записи «MNIST
дал 94% при `K=2`» нечем восстановить, каким кодом это посчитано. Принятое
соглашение о ветках дыру расширяет — после `git branch -D` неудачной гипотезы её
коммиты недостижимы, и хеш остаётся единственной ниточкой (обычно к тегу
`exp/<имя>`).

Флаг `dirty` оказался не менее важен, чем сам хеш: при отладке правки не
коммитятся, и хеш врёт ровно тогда, когда точность нужнее всего. Незакоммиченное
дерево даёт warning в логе — «прогон точно не воспроизводим».

**Сломалось.** Ничего. Отсутствие git или репозитория прогон не роняет —
проверено тестом, иначе облачный образ без git ронял бы всю очередь.

**Соглашение о работе** зафиксировано в `CLAUDE.md`: все изменения через ветку,
`LOG.md` правится только на `main` (иначе вывод из неудачной гипотезы исчезнет
вместе с веткой). Туда же уехали выводы блока 0, ставшие правилами: параллельные
процессы вместо GPU-оптимизации, «сначала подозревай измеритель», требования к
логам и именам прогонов.

**Следующее действие.** Сессия 1.0: перечитать §3.1–3.5 `research-plan.md` и
выписать в псевдокод формулы `e = a·psi(z)`, обновления `W_ff += lr·outer(e, pre)`,
трейса и baseline-вычитания — с явной фиксацией размерностей каждого тензора.
Результат — раздел «формулы» в `notes/`, к которому дальше сверяется код.

## V.4 — повторный запуск и наблюдаемая веб-очередь (2026-08-15)

**Сделано.** Карточка прогона теперь клонирует конфиг, позволяет изменить
разрешённые гиперпараметры, показывает diff и ставит новый запуск в существующую
очередь на `ProcessPoolExecutor`. Новый каталог резервируется атомарно до
`submit`: браузер сразу получает `run_id`, открывает карточку со статусом
`queued`, а worker переводит её в `running` и терминальное состояние. Новый
`config.json` и `run.json` содержат `parent_run_id`; исходный каталог не
изменяется.

Web API не доверяет форме: набор ключей и типы значений перепроверяются на
сервере. `experiment`, модель, датасет, исследовательская метка и пути нельзя
изменить из браузера, поэтому повторный запуск не превращается в удалённый импорт
произвольного Python-модуля или чтение произвольного пути.

Следующим этапом V.5 добавлено сравнение: baseline и до четырёх кандидатов, diff
конфигов, дельты итоговых метрик и кривые на общих графиках. Для ребёнка baseline
по умолчанию берётся из `parent_run_id`. Более поздний блок 2 теперь расширяет
сравнение агрегацией по сидам и доверительными интервалами, а не повторяет
базовый UI.

**Проверено.** Полный набор из 68 тестов проходит. Отдельный end-to-end smoke на
Windows прогнал настоящий `ProcessPoolExecutor`: `queued → running → completed`,
с сохранением `parent_run_id` и `metrics.json`. UI запущен на реальном каталоге
`runs/` и открыт в браузере. После просмотра фоновый Uvicorn и его обёртки
остановлены, порт 8000 освобождён.

**Сломалось.** Первый process-pool smoke завершил вычисление успешно, но stdout
worker-процесса оказался CP1251: символ `→` вызвал `UnicodeEncodeError` внутри
`logging` и напечатал ложный traceback после успешного результата. Файловый лог
UTF-8 не пострадал. Консольный formatter теперь учитывает `sys.stdout.encoding`,
транслитерирует стрелки и безопасно заменяет неподдерживаемые символы; повторный
smoke прошёл без logging error.

**Что запомнить.** Мок scheduler проверяет HTTP-контракт, но не проверяет Windows
`spawn`, импорт дочернего процесса, реальные переходы состояния и кодировку
консоли — для изменений очереди обязателен короткий настоящий прогон. Наблюдаемая
очередь должна создать идентичность и сохраняемое состояние задачи до передачи в
executor. Даже локальный UI остаётся границей исполнения: выбирать код и пути из
браузера нельзя. Наконец, повторный запуск без соседнего сравнения отвечает на
«что запустили», но не на исследовательский вопрос «к чему привело изменение».

Кнопку остановки сервера пока не добавляем. При запуске Uvicorn с `--reload`
приложение живёт в дочернем процессе reloader-а, поэтому self-shutdown может
остановить не тот процесс. Штатный путь разработки — видимый терминал и
`Ctrl+C`; отдельную команду `bioplast.viz serve` имеет смысл вводить только
вместе с принадлежащим приложению lifecycle без `--reload`.

**Следующее действие.** Сессия V.5: API и экран сравнения запусков. Выбор одного
baseline и до четырёх кандидатов; по умолчанию родитель/ребёнок через
`parent_run_id`; diff конфигов, абсолютные дельты итоговых метрик и общие графики
по фактическому `step`/`epoch` без выдуманной интерполяции. Несовместимые
эксперименты, модели, датасеты и отсутствующие ряды показывать явно.

## V.5 — сравнение запусков (2026-08-16)

**Сделано.** Добавлены API и отдельный экран сравнения одного baseline с числом
кандидатов до четырёх. Экран показывает различия конфигов, итоговые значения и
абсолютные дельты метрик, а также накладывает временные ряды на общие графики по
их настоящим `step`/`epoch`. Связанные прогоны удобно открываются из карточки;
для ребёнка baseline автоматически выбирается по `parent_run_id`. Сам
`parent_run_id` из diff исключён: это связь между запусками, а не изменённый
параметр эксперимента.

Графики различают baseline более толстой линией и открытыми маркерами. Колесо
мыши прокручивает страницу, пока пользователь не активирует график кликом;
после активации доступны zoom и панорамирование левой кнопкой, выход — кликом
снаружи или `Escape`. Сброс масштаба расположен в собственной полосе под осью.
Подсказки не занимают место внутри графика. Селекторы baseline и кандидатов
ограничены собственной колонкой и больше не перекрываются на узком экране.

**Проверено.** Полный набор из 79 тестов проходит. Покрыты расчёт diff и дельт,
несовместимые и отсутствующие ряды, ограничения числа запусков, API и ключевые
элементы страницы сравнения.

**Сломалось.** Функциональных дефектов не осталось. В тестах по-прежнему есть
предупреждение Starlette об устаревающем способе передачи приложения в `httpx`
через `TestClient`; оно не связано с V.5.

**Что запомнить.** Служебная lineage-метаинформация не должна выглядеть как
экспериментальная разница. На графиках с несколькими рядами baseline обязан
отличаться не только цветом. Интерактивный график не должен перехватывать колесо
при обычной прокрутке страницы; явная активация хорошо отделяет навигацию по
странице от исследования данных. Для сложных grid-колонок недостаточно одной
ширины: `minmax(0, ...)` и `min-width: 0` нужны, чтобы длинные идентификаторы не
выталкивали соседние элементы.

**Следующее действие.** Сессия V.6: определить независимый от UI протокол
инспекции модели и экспортировать для backprop-XOR граф слоёв и связей со
сводкой тензоров — именами, формами, dtype и безопасной статистикой весов. Затем
закрепить формат контрактными тестами, чтобы V.7 мог визуализировать модель, не
зная деталей её Python-реализации.

## Подготовка V.6 — граница live-инспекции и рабочий ритуал (2026-08-16)

**Сделано.** Уточнена граница между браузером и работающей моделью. UI не
владеет живым объектом PyTorch, но это не запрещает двусторонний обмен:
инспектор внутри worker-процесса читает веса, активации и другие состояния после
атомарных операций, сериализует согласованный снимок и может сразу передать его
браузеру. Live-канал не обязан ждать записи на диск; он использует ту же
версионированную схему и номера событий, а файловые артефакты остаются
каноническими для воспроизведения. Входные данные и команды UI возвращаются
через типизированный протокол и применяются worker-процессом только в безопасных
точках. Запрещены прямые ссылки на изменяемые Python-объекты, неатомарное чтение
и произвольные вызовы кода, а не наблюдение и управление сетью.

Добавлены две repo-команды Codex. `$finish-stage` выполняет проверку, commit,
rebase, fast-forward merge, запись в журнал и push. `$continue-work` полностью
перечитывает правила и каноническую документацию, восстанавливает ближайшее
действие и продолжает работу. Между ними пользователь отдельно вызывает
встроенную команду интерфейса `/compact`; skill не притворяется, что способен
сам управлять контекстом приложения.

**Проверено.** Оба skill проходят официальный `quick_validate.py`, обнаруживаются
установленным Codex из `.agents/skills`, а `git diff --check` не находит ошибок.
Полный pytest не запускался: исполняемый код приложения не менялся.

**Сломалось.** Генератор metadata и валидатор skill по умолчанию использовали
системную CP1251 на Windows. Первый создал невалидный UTF-8 `openai.yaml`, а
второй не смог прочитать корректный UTF-8 `SKILL.md`. Metadata пересозданы в
UTF-8; валидатор запускается с `PYTHONUTF8=1`.

**Что запомнить.** Граница процесса нужна для согласованности, безопасности и
воспроизводимости, но не должна превращаться в запрет live-диагностики. Данные
разрешено передавать немедленно, если они получены в безопасной точке и имеют
тот же контракт, что сохраняемая копия. Повторяемые агентские ритуалы следует
оформлять как repo-scoped skills; действия интерфейса вроде `/compact` остаются
явными пользовательскими шагами.

**Следующее действие.** Сессия V.6: спроектировать schema version 1 для
`model.json` и сводки тензоров, реализовать независимый от UI инспектор
backprop-XOR и закрепить экспорт контрактными тестами. Инспектор должен работать
как со статическим экспортом, так и в будущих согласованных live-точках без
изменения формата данных.

## V.6 — инспекция модели и бинарный checkpoint (2026-08-16)

**Сделано.** Реализован независимый от UI PyTorch-инспектор. В согласованной
точке он выполняет observation-forward, восстанавливает training-флаги и
возвращает только сериализуемый граф leaf-модулей и tensor payload версии 1.
Payload содержит имя, роль, форму, dtype, `requires_grad`, конечную статистику,
число `NaN`/`Inf` и, только для малых конечных тензоров, полные значения. Лимит
raw values по умолчанию равен 256 элементам; большие веса не раздувают JSON.

Backprop-XOR теперь пишет `model.json` с графом `hidden → output`, формами,
активациями, сводками и полными малыми `weight`/`bias`. Полное состояние вынесено
в отдельный атомарный `checkpoint.pt`: versioned-заголовок,
`model_state_dict`, `optimizer_state_dict` Adam и номер шага. Целый `nn.Module`
не сериализуется; архитектура создаётся versioned-кодом из `config.json`, а
checkpoint загружается с `weights_only=True` и заданным `map_location`.

**Проверено.** Полный набор из 85 тестов проходит. Контрактные тесты проверяют
копирование малых тензоров без живой ссылки, size limit, безопасное представление
`NaN`/`Inf`, граф и формы XOR, восстановление training-режимов и интеграционный
экспорт реального прогона. Отдельный round-trip восстановил веса модели и
внутреннее состояние Adam из `checkpoint.pt`. Реальный XOR `2→8→1` снова решил
задачу (`loss ≈ 1e-5`, `acc = 1.0`) и создал оба артефакта. Перед завершением
Uvicorn остановлен, порт 8000 освобождён.

**Сломалось.** Первоначальная формулировка смешивала инспекционное представление
с хранением обученной модели: один JSON не подходит для большой модели,
inference и дообучения. Форматы разделены до появления UI V.7. Функциональных
дефектов не осталось; в pytest сохраняется прежнее предупреждение Starlette о
deprecated-интеграции `httpx` через `TestClient`.

**Что запомнить.** Наблюдаемость и восстановление модели — разные контракты.
UI нужен малый, читаемый и безопасный payload; worker нужен полный state dict и
состояние обучения. Сериализация целого Python-объекта связывает артефакт с
pickle и расположением класса, поэтому сохраняются состояния, а не `nn.Module`.
Граф v1 следует порядку исполнения leaf-модулей и точен для линейного XOR; перед
поддержкой ветвящихся моделей понадобится явная топология, а не предположение о
последовательности вызовов.

**Следующее действие.** Сессия V.7: добавить в карточку запуска секцию модели,
прочитать канонический `model.json`, нарисовать граф `hidden → output` и панель
выбранного слоя с формами, параметрами, tensor summary, числовой таблицей и
heatmap малых весов. Отсутствующий `model.json` у старых прогонов показывать как
нормальное состояние; checkpoint в browser-процессе не десериализовать.

## V.7 — визуализация модели и единый интерфейс экспериментов (2026-08-16)

**Сделано.** Карточка запуска читает канонический `model.json` и показывает
граф слоёв, формы матриц весов, отдельный размер capture-batch, параметры и
активацию выбранного слоя, tensor summary, числовую таблицу и heatmap малых
тензоров. Большие веса не загружаются в браузер целиком: UI показывает их форму,
статистики и причину отсутствия preview. Старые прогоны без `model.json`
остаются валидными и получают понятное пустое состояние.

Все эксперименты переведены на общий `ExperimentResult`. Финальные метрики
возвращаются в `final`, а модель, optimizer, пример forward и описание слоёв —
в `ModelArtifacts`. Worker-раннер централизованно выполняет observation-forward
и создаёт одинаковый комплект `model.json` и `checkpoint.pt`; при ошибке
экспорта он не оставляет частичный комплект. Этим путём теперь пользуются и
backprop-XOR, и backprop-MNIST, поэтому повторный запуск любого из них получает
инспектируемую модель и бинарное состояние для inference или дообучения.

В roadmap зафиксированы следующие уровни визуализации: схема нейронов и связей,
вычислительный граф, heatmap и динамика обучения для малых сетей; обзор блоков,
иерархия модулей, поток тензоров, агрегированная диагностика, профилирование и
поведенческие представления для больших моделей.

**Проверено.** Полный набор из 90 тестов проходит; остаётся известное
предупреждение Starlette о deprecated-интеграции `httpx` через `TestClient`.
Контрактный тест запускает маленькие XOR и MNIST без загрузки внешних данных и
сверяет одинаковые top-level схемы обоих модельных артефактов. Реальный MNIST
`784→256→10` завершился за 7.05 секунды с test accuracy 98.06%, создал
`model.json` и `checkpoint.pt`; headless-browser smoke показал два слоя, batch
128, веса `256×784` и `10×256` и безопасную сводку большой матрицы. Перед
завершением Uvicorn остановлен, порт 8000 освобождён.

**Сломалось.** Повторный запуск старого MNIST сначала не показывал модель:
экспорт артефактов был вручную встроен только в XOR. Исправление отдельного
MNIST-скрипта оставило бы ту же ловушку для следующего эксперимента, поэтому
политика экспорта перенесена в раннер, а прежний произвольный словарь результата
теперь считается нарушением контракта. Функциональных дефектов не осталось.

**Что запомнить.** Общий формат обеспечивается не соглашением между скриптами,
а одним владельцем сериализации. Эксперимент сообщает раннеру живые объекты,
пока они находятся внутри worker-процесса; наружу выходят только versioned JSON
и бинарный state dict. Размер batch описывает конкретный observation-forward,
но не архитектуру: на слоях следует показывать матрицы весов `out×in`, а batch —
отдельным свойством снимка. Полный preview уместен для малых тензоров, для
больших сетей нужны агрегаты и раскрытие по запросу.

**Следующее действие.** Сессия V.8: спроектировать кооперативную машину
состояний `running/paused/completed/failed/cancelled`, типизированные команды
`pause`, `resume` и `step`, безопасные точки применения команд и регулируемую
задержку; затем связать управление с карточкой запуска без выдачи UI живых
PyTorch-объектов.

## V.8 — кооперативное управление запусками (2026-08-16)

**Сделано.** Добавлен типизированный append-only журнал `commands.jsonl` с
монотонными номерами команд `pause`, `resume`, `step`, `set_delay` и `cancel`.
Worker читает его через `CooperativeRunControl` только в safe point перед
атомарной операцией: шагом backprop-XOR, batch backprop-MNIST или итерацией
selftest. Фактические переходы `running ↔ paused` записываются в `run.json`,
одиночный step выдаёт один пропуск и оставляет ручной режим, а отмена завершает
прогон статусом `cancelled`, а не ошибкой.

API и карточка запуска получили чтение control state и отправку команд. UI
различает фактический и уже запрошенный статус, опрашивает их раз в секунду,
показывает только допустимые действия и позволяет задать задержку 0–60000 мс.
Queued-задачу scheduler пытается снять до старта; running-задача отменяется
кооперативно, без убийства процесса посреди обновления весов. Команды переживают
перезагрузку браузера и не зависят от разделяемого живого Python-объекта.

**Проверено.** Полный набор из 97 тестов проходит; остаётся прежнее
предупреждение Starlette о deprecated-интеграции `httpx` через `TestClient`.
Контрактные тесты покрывают валидацию команд, незавершённый хвост JSONL,
pause/resume/step, задержку, queued/running cancel и API-переходы. Отдельный
реальный smoke через Windows `ProcessPoolExecutor` прошёл цепочку
`queued → paused → один шаг → paused → resume → completed`, то есть проверены
не только подменённый scheduler, но и spawn дочернего процесса.

**Сломалось.** Первая реализация задержки использовала один долгий sleep, поэтому
`pause` и `cancel` могли не замечаться до его окончания. Задержка разбита на
короткие polling-интервалы: команда прерывает ожидание до начала следующей
атомарной операции. Других функциональных дефектов к завершению не осталось.

**Что запомнить.** Safe point принадлежит семантике эксперимента: один step —
это законченная операция обучения или inference, а не произвольная строка
Python. Append-only mailbox надёжнее общего изменяемого состояния между HTTP- и
worker-процессами и одновременно даёт воспроизводимую историю команд. UI может
управлять живой сетью и получать согласованные снимки, но владение моделью и
применение команд остаются внутри worker.

**Следующее действие.** Сессия V.9: добавить ручной XOR-вход и выбор одной из
четырёх точек, выполнить forward по слоям через тот же протокол управления и
показать классическую схему нейронов и связей с подсветкой активаций.

## V.9 — интерактивный debug и управление каталогом запусков (2026-08-18)

**Сделано.** Добавлен общий capability-driven debug-протокол
`model_debug_v1` и его первый адаптер `xor_interactive`. Завершённый
backprop-XOR создаёт отдельную дочернюю сессию, worker загружает бинарный
checkpoint, принимает типизированный ручной вход и выполняет скрытый и выходной
слои как отдельные safe-point операции. После каждой фазы атомарно публикуются
snapshot и событие; UI восстанавливает последний согласованный слой и показывает
активации, вклад и знак связей на схеме «кружки и стрелки». Непрерывный режим
сам выполняет полный forward, а пошаговый использует тот же контроллер.

Debug-возможности больше не выводятся из имени XOR: конфиг объявляет protocol,
renderer, форму входа и поддержку step. Поэтому следующие модели смогут
подключить собственный loader/input adapter и представление без новой машины
управления. В документации спроектирован V.10 `RunSupervisor`: отдельные
main/debug executors, скользящая activity lease, heartbeat, гибернация и
recovery того же `run_id` после timeout, crash, restart или power loss. Для
обычного обучения отдельно запланирован resume с model/optimizer, batch/sampler
и состояниями RNG.

Каталог запусков получил server-side пагинацию, явный debug-шильдик и фильтр,
обычный select эксперимента, список дочерних debug-сессий в карточке родителя и
обратную ссылку из сессии. Терминальные запуски можно удалить по одному или
группой; активные удалять нельзя, а родитель требует включить в запрос всех
детей, чтобы не оставлять битые ссылки. Static assets получили cache-busting,
чтобы HTML/JavaScript не расходились после обновления.

**Проверено.** Полный набор из 107 тестов проходит; остаётся прежнее
предупреждение Starlette о deprecated-интеграции `httpx` через `TestClient`.
Реальный Windows `ProcessPoolExecutor` проверил создание debug-сессии, команды,
ручной вход и послойные snapshots. Пользователь визуально подтвердил шильдики,
фильтр и select на реальном каталоге: API увидел 20 запусков, из них 5 debug, а
`include_debug=false` вернул 15. Перед завершением остановлены все найденные
экземпляры Uvicorn на портах 8000, 8001 и 8765; процессов
`bioplast.viz.api:app` не осталось.

**Сломалось.** Сначала «Подать вход» конфликтовала с polling control state:
кнопка зависала или команда считалась принятой до фактического forward. Введены
revision и явное ожидание завершённого output snapshot. `cancel` оказался
терминальной операцией, а не выходом из пошагового режима; UI теперь отделяет
его от `resume`. Долгоживущая paused debug-сессия заняла единственный worker и
задержала MNIST — это выявило необходимость отдельного debug executor и
гибернации. Наконец, старый backend без `--reload` отдавал новый `runs.js`, но
старый API без `is_debug`: фильтр визуально существовал, но ничего не менял.

**Что запомнить.** Debug — свойство протокола и адаптера модели, а не имя
эксперимента и не XOR. Пауза вычисления не равна отсутствию пользователя:
активная сессия должна сохранять один worker, продлевать lease на месте и писать
recovery на каждом safe point; новый процесс нужен только после гибернации или
сбоя. UI и backend должны обновляться согласованно, а проверять интерфейс нужно
на фактическом API запущенного процесса, не только по файлам static на диске.
Нативный `datalist` непредсказуемо позиционируется браузером; для конечного
набора экспериментов обычный `select` надёжнее.

**Следующее действие.** Реализовать V.10 `RunSupervisor`: отделить debug workers
от main pool, ввести worker/activity leases и heartbeat, сохранять постоянный
recovery-checkpoint, переводить неактивную сессию в `suspended` и продолжать тот
же `run_id` после пробуждения, падения процесса или перезапуска машины.

## V.10 — долговечный supervisor и восстановление debug-сессий (2026-08-19)

**Сделано.** Общий scheduler заменён на `RunSupervisor` с независимыми main и
debug исполнителями. Ожидающая пользовательского ввода debug-сессия больше не
занимает слот обычного обучения. Для каждого worker введены атомарный claim,
номер attempt и heartbeat в `worker.json`; пользовательская активность хранится
отдельной скользящей lease и продлевается только командами, открытием карточки и
throttled heartbeat видимой вкладки после реального взаимодействия. Фоновый
polling lease не продлевает.

XOR debug после отсутствия пользователя сохраняет согласованное состояние и
переходит в `suspended`, освобождая процесс. `resume`, `step` или `set_input`
создают новый debug worker, проверяют checksum и версию adapter, затем продолжают
тот же `run_id` со следующей фазой `input → forward_hidden → forward_output`.
При старте supervisor stale lease переводится в `interrupted`; повреждённый
recovery остаётся доступен для инспекции с явной причиной недоступности resume.
Итоговый `checkpoint.pt` не смешивается с runtime recovery: бинарные состояния
публикуются неизменяемыми поколениями, а `recovery/state.json` атомарно
переключается последним.

API и карточка показывают pool, attempt, worker heartbeat, activity lease,
recovery generation и safe-point cursor. Добавлены статусы `suspended` и
`interrupted`, пробуждение неактивной сессии и отдельная терминальная отмена.
Документы контрактов, API, UI, lifecycle, roadmap и README приведены к V.10.

**Проверено.** Полный набор из 111 тестов проходит; остаётся прежнее
предупреждение Starlette о deprecated-интеграции `httpx` через `TestClient`.
Реальные Windows spawn-тесты подтвердили, что debug и main выполняются
одновременно, inactivity освобождает процесс, новый attempt продолжает тот же
run без повторных событий, corrupted checksum запрещает resume, а startup
reconciliation отличает stale lease. Отдельный end-to-end сценарий прошёл
pause/step/resume/cancel и послойный XOR forward после гибернации.

**Сломалось.** Первые тестовые leases были короче импорта PyTorch, поэтому новый
worker успевал снова уснуть до обработки команды; начало lease перенесено к
фактическому входу в эксперимент. Замена одного `recovery/checkpoint.pt`
создавала окно, где старый `state.json` видел уже новый бинарник и ложный
checksum mismatch; бинарники сделаны неизменяемыми по поколениям. Затем полный
spawn-suite поймал Windows `WinError 5` при `os.replace(run.json.tmp, run.json)`,
когда UI одновременно читал цель: atomic writer получил уникальные temp-файлы и
ограниченный retry sharing violation. Два старых smoke-теста также использовали
один накопительный deadline на несколько независимых фаз; deadline разделён по
переходам.

**Что запомнить.** Атомарность пары файлов нельзя получить двумя последовательными
`replace`: нужен неизменяемый payload и один атомарно переключаемый указатель.
Append-only событие и recovery тоже имеют узкое окно, поэтому при восстановлении
adapter обязан согласовать сохранённый cursor с уже опубликованным хвостом
`events.jsonl`. Activity пользователя, жизнь worker и научное состояние — три
разных факта и должны иметь разные долговечные контракты. На Windows атомарная
замена логически корректна, но требует retry краткого sharing violation.

**Следующее действие.** Сессия V.11: добавить recovery-adapter обычного обучения
для backprop-XOR и MNIST — сохранять model/optimizer, epoch/batch/global step,
permutation/sampler и состояния Python/NumPy/torch CPU/CUDA RNG, затем проверить
продолжение interrupted запуска с последней safe point настоящим Windows spawn.
