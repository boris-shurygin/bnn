# Журнал сессий

Ритуал: **каждая** сессия заканчивается записью — что сделано, что сломалось,
**следующее конкретное действие**. Последнее формулируется как задача на час
(«написать `ThreeFactorLayer.forward` и тест на совпадение с `nn.Linear+ReLU`»),
а не как направление («продолжить работу над слоем»).

Никогда не заканчивать на сломанном коде: лучше откатить и закоммитить рабочее.

Формат записи:

```
## <номер сессии> — <заголовок>            (дата)
**Сделано.** …
**Сломалось.** …

```

## 0.1–0.6 — блок 0: каркас и точка отсчёта (2026-08-08)

Шесть сессий роадмапа сделаны подряд, одной серией. Ниже — по пунктам плана.

**Сделано.**

*0.1 Репозиторий и окружение.* `uv` 0.12.3 (`~/.local/bin`), venv на CPython
3.12.10, torch 2.6.0+cu124 из индекса PyTorch, `torch.cuda.is_available() = True`,
RTX 3060 видна. `pyproject.toml` + `uv.lock`, `.gitattributes` с `eol=lf`,
`runs/`, `queue/`, `data/` в `.gitignore`. Каркас `src/bioplast/`, `experiments/`,
`tests/`. pytest — 22 теста, зелёные.

*0.2 Журнал и раннер.* Этот файл. Раннер: конфиг-файл → `runs/<id>/{config,metrics}.json`
+ `run.log`; идентификатор короткий (`mnist-bp-s0-d0a098`) из-за лимита пути в
260 символов. Очередь — `ProcessPoolExecutor` с параметром `--workers`.
Падение эксперимента пишется в `metrics.json` со `status: failed` и очередь не
роняет. `bioplast.runner.sweep` разворачивает базовый конфиг по сетке значений
(`--set seed=0,1,2`) — свипы блока 2 не придётся писать руками.

*0.3 XOR-эталон.* `2→8→1`, ReLU, BCEWithLogits, Adam lr=0.05. Три сида, все
решают: loss `1e-5…7e-5`, точность 1.00, решение на шагах 43 / 43 / 49 из 2000.

*0.4 MNIST-эталон.* `784→256→10`, Adam lr=1e-3, батч 128, 10 эпох. Тест
**98.06 / 98.08 / 97.90 %** на сидах 0/1/2 — ориентир роадмапа (~98%) взят.
Датасет качается скриптом с зеркала OSSCI, кэшируется в `.npz` и целиком уезжает
на GPU; `DataLoader` не используется.

*0.5 Диагностика v0.* `diagnostics/`: регистратор метрик с плоскими ключами
`группа/имя` и замеры — нормы весов, нормы градиентов, RMS / максимум / разреженность
активаций. `act_max` заведён сразу как сторож runaway для абляции §3.5.

*0.6 `plot.py`.* `metrics.json` → PNG по одной группе метрик на файл. Скрипт не
знает ничего про конкретный эксперимент: новая метрика в эксперименте
автоматически появляется на графике.

**Сломалось.**

- Store-сборка Python (`WindowsApps`) — неудобная база для venv; `uv` создал
  окружение поверх неё без проблем, но при первой же странности стоит перевести
  проект на `uv python install`.
- Первая версия критерия «XOR решён» смотрела только на точность. На четырёх
  точках случайная инициализация угадывает все четыре с вероятностью 1/16, и
  прогон рапортовал «решено на шаге 6». Критерий ужесточён до «точность 1.0 **и**
  loss < `loss_target`» — стало 43–49.
- `np.frombuffer` отдаёт read-only массив, torch на это ругается; добавлен `.copy()`.
- `python -m bioplast.viz.plot` предупреждал о двойном импорте (модуль
  реэкспортируется в `__init__`); CLI вынесен в `viz/__main__.py`.

**Замеры для памяти.** XOR (CPU) — 7.5 с на прогон, из них секунды на импорт
torch. MNIST (GPU) — 12 с последовательно, 9.2 с при трёх параллельных процессах:
карта не загружена, параллельность работает ровно так, как обещал роадмап.
Свип из 45 конфигураций блока 2 — это порядка 7 минут, а не полутора часов.

## 0.7 — проверка, что вычисления действительно на карте (2026-08-08)

Вне плана, по ходу разбора блока 0.

**Сделано.** Лог окружения переделан: имя карты пишется только если прогон
реально на ней (было `device = cpu (RTX 3060)` — читается как «работаем на
3060»), добавлено `cuda_build` (у CPU-сборки torch это `None` — главный признак
беды) и пиковая VRAM за прогон. Ноль VRAM при `device=cuda` означает, что
эксперимент проигнорировал `ctx.device`, — теперь это warning в логе и два теста.
Эксперименты дополнительно печатают, на каком устройстве лежат веса.

**Замер CPU vs GPU, MNIST `784→256→10`, 3 эпохи:**

| Устройство | Время | Пиковая VRAM |
|---|---|---|
| CPU | 2.57 с | — |
| RTX 3060 | 1.92 с | 360 МБ |

Выигрыш всего 1.3×. Это не поломка, а ровно то, что предсказывал роадмап:
на моделях блоков 0–3 узкое место — задержки запуска ядер, а не вычисления.
Отсюда практический вывод, который стоит помнить весь блок 2: **ускорение даёт
не карта, а параллельные процессы** (3 прогона одновременно давали 9.2 с против
12 с последовательно). 360 МБ пиковой VRAM подтверждают, что датасет целиком
уехал на карту, как и задумано.

## 0.8 — именование прогонов и логи (2026-08-08)

**Сделано.** В логах теперь полная дата, а не только время: прогон разбирают не
в день запуска, и «14:30:12» без числа бесполезен.

Имена папок в `runs/` переделаны под сортировку и читаемость:
`20260808-095245-ses0.4-mnist-mlp-784-256-10-s0-bp`. Метка времени первой
компонентой — сортировка по имени совпадает с хронологической; дальше сессия
роадмапа, датасет, модель, сид, короткий комментарий. Компоненты берутся из
полей конфига `session` / `dataset` / `model` / `tag`: раннер не может вывести
«что за модель» из кода эксперимента, а угадывать по `hidden` — значит завязаться
на конкретный эксперимент.

Важное следствие, которое пришлось развести явно: **имя папки прогона и имя
файла конфига в очереди — разные вещи**. Папка временна́я (каждый запуск —
новая), файл конфига детерминированный (`ses0.4-mnist-…-s0-bp-4d0835.json`),
иначе перегенерация свипа плодила бы дубли вместо перезаписи. Отсюда две
функции — `make_run_id` и `config_slug`.

Прогоны, стартовавшие в одну секунду (очередь на 3–4 воркерах — обычное дело),
разводятся суффиксом `-2`, `-3`.

**Сломалось.** Ничего; старые папки `runs/` со схемой `mnist-bp-s0-d0a098`
удалены и эталоны перегенерированы, чтобы в папке не жили две схемы разом.

## 0.9 — привязка прогона к состоянию кода (2026-08-08)

**Сделано.** `metrics.json` теперь содержит блок `git`: хеш коммита, ветка,
признак незакоммиченных правок и список изменённых файлов.

Дыра была настоящая: `runs/` не версионируется, и через месяц по записи «MNIST
дал 94% при `K=2`» нечем восстановить, каким кодом это посчитано. Принятое
соглашение о ветках дыру расширяет — после `git branch -D` неудачной гипотезы её
коммиты недостижимы, и хеш остаётся единственной ниточкой (обычно к тегу
`exp/<имя>`).

Флаг `dirty` оказался не менее важен, чем сам хеш: при отладке правки не
коммитятся, и хеш врёт ровно тогда, когда точность нужнее всего. Незакоммиченное
дерево даёт warning в логе — «прогон точно не воспроизводим».

**Сломалось.** Ничего. Отсутствие git или репозитория прогон не роняет —
проверено тестом, иначе облачный образ без git ронял бы всю очередь.

**Соглашение о работе** зафиксировано в `CLAUDE.md`: все изменения через ветку,
`LOG.md` правится только на `main` (иначе вывод из неудачной гипотезы исчезнет
вместе с веткой). Туда же уехали выводы блока 0, ставшие правилами: параллельные
процессы вместо GPU-оптимизации, «сначала подозревай измеритель», требования к
логам и именам прогонов.

**Следующее действие.** Сессия 1.0: перечитать §3.1–3.5 `research-plan.md` и
выписать в псевдокод формулы `e = a·psi(z)`, обновления `W_ff += lr·outer(e, pre)`,
трейса и baseline-вычитания — с явной фиксацией размерностей каждого тензора.
Результат — раздел «формулы» в `notes/`, к которому дальше сверяется код.
